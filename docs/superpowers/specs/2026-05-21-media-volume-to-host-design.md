# Media volume → host bind mount — design

## Goal

Relocate production media (user uploads) from the Docker named volume
`dataetipitaka_media_volume` to a host folder, so the files sit at a known
host path that can be backed up, rsynced, or inspected without Docker
commands. Scope is the relocation only — no backup automation.

## Context

- Repo: `~/data.etipitaka` on the production server (`data.etipitaka.com`).
- `docker-compose.yml` defines a `media_volume` named volume, mounted into
  both `web` and `nginx` at `/home/app/web/media`.
- Current media volume: ~279 MB, 4326 files.
- Media files in the volume are owned by **uid 100 / gid 101** (the retired
  Python 2 stack's user). The current container's `app` user is **uid 999**.
  The files are world-readable, so the new stack can read media, but new
  uploads would target 100-owned directories the `app` user cannot write.

## Decisions

- **Host path: `~/data.etipitaka/media`** (i.e. `./media` relative to the
  compose file). Convenient — next to `docker-compose.yml` — at the cost of
  needing a `.gitignore` entry.
- **Cutover: Approach A — stop, copy, switch, start.** A ~1-2 minute
  downtime window is acceptable for a 279 MB volume, and it carries no risk
  of losing an upload that would otherwise land between a live copy and the
  switch.
- **chown the host folder to `999:999`** as part of the move, so the `app`
  user can both read existing media and write new uploads. This also
  corrects the pre-existing uid mismatch (100 → 999).
- **Manual cutover, not a pipeline deploy.** The data copy must complete
  before the new compose config is active; otherwise the containers mount
  an empty `./media`. The pipeline cannot do the one-time copy + chown.
- Media only — `static_volume` stays a named volume (regenerated by
  `collectstatic`, no backup value).

## Changes

### `docker-compose.yml`
- `web` service volumes: `media_volume:/home/app/web/media` →
  `./media:/home/app/web/media`
- `nginx` service volumes: same substitution
- Remove `media_volume` from the top-level `volumes:` block. Keep
  `static_volume` and `postgres_data`.

### `.gitignore`
- Add `media/` so the 4326 media files are never committed (`static/` is
  already ignored).

## Cutover procedure (server, one maintenance window)

1. `docker compose stop web nginx` — `db` stays up.
2. `mkdir -p ~/data.etipitaka/media`
3. Copy volume → host folder, preserving attributes:
   `docker run --rm -v dataetipitaka_media_volume:/src -v ~/data.etipitaka/media:/dst alpine cp -a /src/. /dst/`
4. `sudo chown -R 999:999 ~/data.etipitaka/media`
5. `git pull --ff-only` (brings in the new compose + `.gitignore`), then
   `docker compose up -d`.

## Verification

- An existing media URL returns HTTP 200.
- A new file upload succeeds and lands in `~/data.etipitaka/media` — proves
  the `app` user (999) can write.

## Rollback

Revert the `docker-compose.yml` change and `docker compose up -d`. The
named volume `dataetipitaka_media_volume` is left untouched throughout, so
the original data is intact. Delete the old volume only after the bind-mount
setup is confirmed working.

## Out of scope

- Backup automation (cron, rsync schedule) — the user backs up the folder
  themselves.
- Relocating `static_volume` or `postgres_data`.
